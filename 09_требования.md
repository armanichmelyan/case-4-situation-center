# Требования к ситуационному центру — кейс 4

## Как заполнять

Даны по одному образцу FR и NFR. Заполни FR-2…FR-10 и NFR-2…NFR-5.
В колонке «Тест» укажи ID из `03\_тесты.md` или «—».

## 1\. Функциональные требования (FR)

|ID|Требование|Приоритет|Тест|
|-|-|-|-|
|FR-1|Принять показатель от датчика (time, location, indicator, value)|Must|T4-2|
|FR-2|Принимать инцидент из мобильного приложения|Must|T4-1|
|FR-3|Рассчитывать severity по формуле процентного отклонения от границ нормы|Must|T4-2|
|FR-4|Создавать оповещения WARNING, CRITICAL и STALE|Must|T4-2, T4-5|
|FR-5|Эскалировать оповещения CRITICAL и STALE руководителю|Must|T4-5|
|FR-6|Не создавать повторный алерт для одинаковых location + indicator в окне 5 минут|Must|T4-4|
|FR-7|Поддерживать жизненный цикл инцидента NEW → ASSIGNED → IN_PROGRESS → CLOSED и закрытие ложного вызова из ASSIGNED с причиной NO_ACTION|Must|T4-1|
|FR-8|Проверять роль пользователя и разрешенную ему зону при смене статуса инцидента; начало работы разрешать только назначенному инженеру|Must|T4-1|
|FR-9|Записывать создание инцидента и каждый переход статуса в аудит|Must|T4-1|
|FR-10|Отклонять события с пустым или неизвестным location|Must|T4-3|

**Дополнительно по правилу A-3 из 02_правила.md:** два последовательных CRITICAL для одной пары location + indicator в пределах 15 минут должны создавать автоинцидент с source=auto. Подавление повторного алерта не должно мешать созданию автоинцидента. Уточнение команды, принятое в прототипе: если по тому же датчику уже есть открытый инцидент, еще один не создается.

**Связь с тестами:** ID в таблице обозначает связанный сценарий, а не полное покрытие требования. T4-1 проверяет создание и назначение инцидента и две записи аудита; остальные переходы, запреты и разграничение по зонам проверены дополнительно. T4-2 проверяет WARNING, T4-5 — STALE и его эскалацию. CRITICAL и автоинцидент также проверены отдельно и не выдаются за результат этих пяти сценариев.

Приоритет Must для всех десяти требований выбран командой: это основные возможности нашего решения.

**Подсказки для FR-2…FR-10:**

* Приём инцидента из мобильного приложения (T4-1).
* Расчёт severity по формуле deviation\_pct (T4-2).
* Создание алерта WARNING / CRITICAL / STALE (T4-2, T4-5).
* Эскалация CRITICAL и STALE руководителю (T4-5).
* Дедупликация событий в окне 5 минут (T4-4).
* Жизненный цикл инцидента NEW → ASSIGNED → IN\_PROGRESS → CLOSED (T4-1).
* Проверка RBAC при смене статуса (T4-1).
* Запись события в аудит при каждом переходе (все тесты).
* Отклонение события с невалидным location (T4-3).

**Приоритеты:**

* Must — без этого кейс не сдан.
* Should — важно, но не блокирует.
* Could — если останется время.

## 2\. Нефункциональные требования (NFR)

|ID|Требование|Измеримость|
|-|-|-|
|NFR-1|Алерт CRITICAL доставляется диспетчеру ≤ 1 мин|секунды|
|NFR-2|Не создавать повторный алерт для одинаковых location + indicator менее чем через 5 минут после создания предыдущего алерта|минуты; один алерт в пределах окна|
|NFR-3|Определять STALE при отсутствии показаний от датчика более 5 минут|минуты|
|NFR-4|Ограничивать доступ к данным в соответствии с ролью пользователя и разрешенными ему зонами zone_A, zone_B, zone_C|роли × зоны|
|NFR-5|Вести аудит только с добавлением новых записей, без изменения и удаления существующих; хранить записи не менее 90 дней|дни; запрет изменения и удаления|

**Подсказки для NFR-2…NFR-5:**

* Дедупликация в окне 5 минут — минуты.
* STALE определяется через 5 минут после последнего показания — минуты.
* RBAC по зонам (zone\_A, zone\_B, zone\_C) — роли × зоны.
* Аудит append-only, хранится ≥ 90 дней — дни.

## 3\. Ограничения (заполни)

* Реальных датчиков нет: используются исходные синтетические CSV-файлы, а поступление показаний воспроизводится по времени из этих файлов.
* Мобильное приложение не разрабатывается: описывается контракт приема инцидента. В прототипе прием инцидента и действия пользователей моделируются вызовами функций.
* Время на выполнение кейса — 6 рабочих дней и 2 резервных дня.

**Границы прототипа:** уведомления записываются в локальные входящие, а не доставляются по сети на устройство. Проверки сроков выполняются по модельному времени. Журнал аудита дополняется и не удаляется программой; модельный прогон не доказывает физическое хранение на диске 90 суток. Для выполнения этого требования при развертывании нужны права доступа и резервное копирование. Память дедупликации действует в пределах одного запуска; повторное воспроизведение CSV считается новым прогоном.

**Подсказки:**

* Реальных датчиков нет — только CSV-файлы.
* Мобильное приложение не разрабатывается — только контракт приёма инцидента.
* Время на кейс — 6 рабочих дней + 2 резервных.

## 4\. Пользовательские сценарии (заполни)

### Сценарий 1. Датчик превысил порог — диспетчер видит алерт

1. Диспетчер просматривает оповещения участков своей зоны.
2. После поступления температуры 28.3 °C на site_02 при верхней границе нормы 26 °C он видит алерт WARNING.
3. Диспетчер проверяет участок, показатель, время и значение в алерте.
4. Он сопоставляет показание с нормой: отклонение составляет примерно 8.8%, то есть не превышает 10%.
5. Диспетчер определяет дальнейшие действия по предупреждению; автоматическая эскалация как для CRITICAL не выполняется.

**Подсказка:** датчик передал value > norm\_max → Ingestion → Rules Engine → severity WARNING → алерт в списке диспетчера.

### Сценарий 2. Два CRITICAL подряд — диспетчер получает автоинцидент

1. Диспетчер видит CRITICAL по температуре на site_02. Открытого инцидента по этому датчику пока нет.
2. После второго последовательного CRITICAL по той же паре location + indicator в пределах 15 минут он видит новый инцидент со статусом NEW и source=auto.
3. Диспетчер назначает инженера своей зоны: инцидент получает ответственного и статус ASSIGNED. Если второе показание пришло в окне дедупликации, второй алерт не создается, но автоинцидент появляется.

### Сценарий 3. Датчик не передает данные — руководитель получает STALE

1. Руководитель просматривает уведомления по доступным ему зонам.
2. Если от датчика более 5 минут нет показаний, руководитель получает эскалацию STALE с указанием участка и показателя.
3. Руководитель организует проверку связи или датчика. Отсутствие показаний не выдается за измеренное критическое отклонение.

### Сценарий 4. Повтор события — диспетчер не получает второй алерт

1. Диспетчер видит WARNING по температуре на site_02.
2. Через 3 минуты поступает еще одно показание по той же паре location + indicator с тем же уровнем WARNING.
3. В списке диспетчера остается один алерт по этим двум событиям. Повтор получает результат DUPLICATE и не создает лишнего оповещения.

### Сценарий 5. Неизвестный участок — диспетчер получает отказ

1. Диспетчер передает данные нового инцидента с location=site_99, которого нет в справочнике участков.
2. Он получает VALIDATION_ERROR с details: field=location, code=UNKNOWN_LOCATION. Инцидент не создается.
3. Диспетчер выбирает существующий участок из справочника и повторно передает исправленные данные.

**Подсказки для сценариев 2–5:**

* Серия CRITICAL → автоинцидент.
* Датчик offline → STALE + эскалация.
* Повтор события → дедупликация.
* Невалидный location → отказ.

**Важно:** сценарии — от лица диспетчера/руководителя, а не внутренности сервиса.
