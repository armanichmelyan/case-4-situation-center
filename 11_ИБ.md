# Информационная безопасность — кейс 4 «Ситуационный центр»

## Как заполнять

Даны 2 угрозы из 7, 2 меры из 7, 2 строки RBAC, 2 поля аудита.
Заполни остальное. Каждая мера должна ссылаться на ID угрозы.

**Статус документа:** требования к защите и описание текущего учебного прототипа.
Код дорабатывает второй участник; после его изменений реализацию нужно сверить
с этим документом. Вероятности, ущерб, остаточные риски и порядок ротации —
качественные оценки и решения команды, а не статистика из исходных CSV.
Образцы и подсказки организаторов сохранены.

## 4\. Аудит — структура события (заполни 6 полей из 9)

|Поле|Тип|Пример|Зачем|
|-|-|-|-|
|event\_id|string|evt\_0001|уникальный ID|
|entity\_type|enum|incident|тип объекта|
|entity_id|string|inc_001|идентификатор объекта действия|
|action|enum: created / assigned / status_changed / closed|assigned|вид действия|
|from_status|string, допускается отсутствие|NEW|статус до операции; у создания отсутствует|
|to_status|string, допускается отсутствие|ASSIGNED|статус после операции; у действия без перехода отсутствует|
|actor|string|dispatcher_1|инициатор действия; system для автоматики|
|at|string, ISO 8601|2025-11-01T08:00:00Z|время действия|
|ip|string|10.0.0.1|адрес источника; local у консольного вызова|

**Подсказки для остальных полей:**

* `entity\\\_id` — привязка к объекту (inc\_001).
* `action` — enum: status\_changed / assigned / created / closed.
* `from\\\_status` — статус до перехода.
* `to\\\_status` — статус после.
* `actor` — кто инициировал (e\_101).
* `at` — время (ISO 8601).
* `ip` — откуда (10.0.0.1).

**Правила аудита (ответь):**

* Как хранится журнал? (append-only / можно менять) — append-only: только добавление записей.
* Сколько хранится? — не менее 90 дней по целевому требованию.
* Кто имеет доступ на чтение? — диспетчер и руководитель в разрешенных зонах.

## 5\. Защита данных датчиков (ответь на вопросы)

**Что нельзя:**

* Принимать событие без подписи — нельзя; отказ до обработки показания.
* Доверять `location` из события без сверки с `sites.csv` — нельзя; неизвестный участок отклоняется.
* Хранить оригинальный секрет HMAC в коде — нельзя.

**Что можно:**

* Сверять `signature` через `hmac.compare\\\_digest` — можно и нужно.
* Хранить `SECRET` в переменной окружения — можно; доступ к окружению ограничивается средствами ОС.
* Логировать только `event\\\_id` и `result`, без секретов — можно; ключи, токены и вывод окружения в журнал не попадают.

**Подпись события — напиши формулу:**

Пример для допустимого события; нужны json, hmac, hashlib и os.
Ключ выбирается по проверенным location и indicator.

```python
data = event.copy()
data.pop("signature", None)
payload = json.dumps(data, sort_keys=True, ensure_ascii=False, allow_nan=False).encode("utf-8")
secret = os.environ[key_name].encode("utf-8")
expected = hmac.new(secret, payload, hashlib.sha256).hexdigest()
return hmac.compare_digest(event["signature"], expected)
```

Подписываются все поля, кроме самой signature. На обеих сторонах должны совпадать
поля и сериализация JSON, включая представление чисел. Тип и наличие signature
проверяются заранее. Код показан как тело проверки внутри функции.

## 7\. Соответствие CIA-триаде (заполни)

|Принцип|Как реализован в кейсе|
|-|-|
|Конфиденциальность|RBAC и зоны ограничивают чтение; секреты не выводятся. Для сети требуется TLS. HMAC не шифрует данные.|
|Целостность|HMAC проверяет неизменность сообщения, аудит сохраняет историю. Ручная правка файлов дополнительно ограничивается ОС.|
|Доступность|STALE и эскалация помогают заметить потерю показаний; A-5 снижает поток повторов. Непрерывная работа прототипа не гарантируется.|
|Аутентификация|Токен определяет пользователя; HMAC подтверждает знание общего ключа датчика и приемника.|
|Авторизация|Проверка роли, зоны и назначенного инженера; поле actor само по себе не дает полномочий.|
|Неотказуемость|Аудит с actor и at позволяет разбирать действия внутри приложения; это прослеживаемость, не независимое криптографическое доказательство.|

**Подсказка:** конфиденциальность — HMAC + RBAC по зонам; целостность — append-only аудит + проверка signature; доступность — STALE + эскалация; неотказуемость — аудит с `actor` и `at`.

## 9\. Типичные ошибки (минус баллы)

1. «У нас всё безопасно» — без угроз и мер.
2. Нет HMAC для датчика — любой может подделать CRITICAL.
3. RBAC без разграничения по зонам — диспетчер видит всё.

## 10. Пояснения для реализации и защиты

### Права и зоны

Исходные «да» на создание и назначение также действуют только в разрешенных зонах.
«Все участки» означает все разрешенные участки, а не обход зон. Инженер может читать
справочник своих участков, но в реестре видит только назначенные ему инциденты.
Администратор ведет справочник и не управляет инцидентами.
CLOSED не переоткрывается ни одной ролью. Новая запись не меняет старую.
Из ASSIGNED закрывает только руководитель с NO_ACTION; из IN_PROGRESS —
руководитель после завершения работ. actor сверяется с личностью по токену.

### Аудит: модель и текущие имена

В 08_ER.md используются общие действия created, assigned, status_changed, closed.
В текущем Python им соответствуют incident_created, incident_assigned,
incident_started, incident_closed. Это соответствие имен, а не разные действия.
Журнал также имеет технические записи notified, severity_changed, updated,
rejected и поля location, details. Изменения справочника и отклоненные измерения
могут давать технические записи; ER-модель показывает основные связи инцидентов
и алертов. При переименовании действий в коде соответствие нужно обновить.
Отсутствующий статус в CSV журнала может обозначаться пустой строкой.
ip=local означает локальный вызов, не установленный адрес сетевого клиента.

Программа открывает audit.csv на добавление и не дает функций изменения/удаления.
Ручную подмену файла оператором с доступом к диску прототип не обнаруживает.
Проверка на 100 дней времени сценария не доказывает физическое хранение на диске
90 суток. Для развертывания нужны права ОС, резервное копирование и проверка
восстановления. Общий HMAC-ключ и доступный оператору файл не дают строгой
неотказуемости или независимого доказательства авторства.

### Секреты и ротация

Оценка «низкий» в исходных образцах U-1/U-2 предполагает сохранность ключей,
исправную проверку прав и выполнение мер защиты файлов при развертывании.
HMAC не отличит датчик от человека с украденным ключом.
HMAC не шифрует данные; подсказку про конфиденциальность нельзя трактовать иначе.

При замене секрета доверенный оператор создает случайное значение, обновляет его
у законных сторон, отзывает старое и проверяет отказ со старым значением.
При утечке замена немедленная. Плановая периодичность согласуется отдельно:
в материалах конкретный период не установлен. Прототип читает значения из
окружения; автоматической службы ротации, истечения токенов и защищенной выдачи нет.
Оператор развертывания не равен роли администратора внутри приложения.
В демонстрации ключи могут генерироваться в окружении текущего процесса.
Нельзя пересылать значения секретов или вывод окружения товарищам и в Git.

### Границы прототипа

Реальные датчики и мобильное приложение не разрабатываются.
Сроки проверяются по времени CSV без ожидания в реальном времени, уведомления —
локальные входящие. Принято считать CSV полным потоком: длинные промежутки между
показаниями одного датчика вызывают STALE, новое показание затем оценивается заново.
Память event_id и дедупликации действует в одном запуске. Сохранение этой памяти
между перезапусками остается задачей дальнейшего развертывания.
Непрерывная служба, сетевой TLS-контур и защита файлов ОС здесь не заявляются.

### Что сверить после изменения кода

Отметки критерия приемки подтверждают заполнение проектных разделов и наличие
мер в рассмотренной версии, не независимый аудит промышленной системы.
Второй и третий участники совместно проверяют: подмена и отсутствие подписи
отклоняются; чужая зона недоступна; начинает работу только назначенный инженер;
закрывает только руководитель; тишина датчика вызывает STALE; повтор не создает
второй алерт; создание и переходы сохраняются в истории с actor и at.
